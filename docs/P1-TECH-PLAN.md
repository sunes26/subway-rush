1. `game/public/models/npc/` · `game/public/models/items.glb` 로 복사. 복사는 `npm run assets` 스크립트로 못 박는다 — P0에서 수동 복사였고 "왜 캐릭터가 안 나오지"의 원인이 두 번 이것이었다.

### 2.1 아키텍처 철칙은 안 바뀐다

```
   입력 ──► [순수 시뮬] ──► 상태 ──► [렌더 · UI]
             ▲                          │
             └── 렌더는 상태를 읽기만 한다 ─┘
```

**새 시스템 4개 전부 `(GameState, ctx) => Action[]` 이다.** 렌더를 모른다.
그래서 **효자손 체인 전체를 헤드리스로 시뮬레이션할 수 있다** — 이게 P1의 인수 기준 B-1을 20ms에 검증하는 유일한 방법이다.

**예외 1건(의도적)**: 마우스 델타. QTE 입력은 `InputFrame.lookYaw`의 **프레임간 차분**이다. 이미 InputFrame에 있으므로 경계는 유지된다 — 시스템은 여전히 DOM을 모른다.

### 2.2 tick 파이프라인 — 삽입 순서와 그 근거

```ts
// systems/tick.ts
s = ADVANCE(dtMs)                       // 1) 시계
train = trainAt(s.elapsedMs)            // 2) 열차 = 시간의 순수 함수
rebuildDynamics(s)                      // 3) 동적 충돌체 = 게이트 플랩 + PSD + ★NPC 몸통 + ★인파벽
s += movementSystem(s, ctx)             // 4) 이동 (MOVE 전량 스냅샷)
s += chaseSystem(s, ctx)                // 5) ★추격 — 이동 후 위치를 봐야 거리 판정이 맞다
s += crowdSystem(s, ctx)                //    ★인파 — 밀어내기는 MOVE 재발행 (gateKnockback 선례)
s += interactSystem(s, ctx)             // 6) ★상호작용 — 최종 위치에서 타겟팅
s += qteSystem(s, ctx)                  //    ★QTE — interact가 켠 세션을 같은 틱에 진행
s += gatesSystem(s)                     // 7) 개찰구 (위치 기반, 키 입력 없음)
s += gateKnockback(s, before)
s += trainSystem(s)                     // 8) 탑승
zone / 종료 판정                          // 9)
```

**순서가 규칙인 이유 3가지**
- 추격이 이동보다 **뒤**여야 한다: 앞이면 플레이어가 이미 도망친 위치를 못 보고 한 프레임 늦게 때린다 (16.7ms × 걷기 5m/s = 8cm — 반경 1.2m에서 티가 난다)
- 밀어내기(`crowd`)와 넉백(`gateKnockback`)은 둘 다 **MOVE 전량 재발행**이다. `movementSystem`의 MOVE를 덮어쓰므로 반드시 뒤에 온다
- `interact`가 `qte`보다 앞: E를 누른 그 틱에 QTE가 시작되고 같은 틱에 첫 델타를 먹는다. 반대면 1프레임 입력이 버려진다

## 3. 핵심 기능 작동 방식

### 3.1 F-P1-01 상호작용 — **레이캐스트를 쓰지 않는다**

GDD는 "마우스 hover"라 썼고 1인칭에선 그게 크로스헤어다. 순진한 구현은 `Raycaster`인데, **그러면 시뮬이 씬을 알아야 한다.** 대신 각도로 판정한다.

```ts
// systems/interact.ts (개념)
const dir = { x: Math.cos(ctx.cameraYaw), y: Math.sin(ctx.cameraYaw) }   // camera-rig 규약: 월드 yaw 0 = +x

for (const it of candidates(s)) {           // 존 필터 + consumed 필터
  const d  = dist2D(p, it)
  if (d > INTERACT.reachM) continue          // 3.0
  const cos = dot(normalize(it - p), dir)
  const ang = Math.acos(cos)
  if (ang < INTERACT.aimRad && d <= INTERACT.reachM) → 조준 후보 (ang 최소가 승리)
  else if (d <= INTERACT.nearM) → 근접 후보 (d 최소가 승리)
}
```

| 상수 | 값 | 근거 |
|---|---:|---|
| `INTERACT.reachM` | 3.0 | GDD §5.1의 hover는 거리 제한이 없지만, 1인칭에서 3m 넘으면 "저 멀리 게 왜 켜지지"가 된다 |
| `INTERACT.nearM` | 1.5 | GDD §5.1 · §11 판정 반경 그대로 |
| `INTERACT.aimRad` | 0.61 (35°) | FOV 74°의 절반이 37°. 화면 안이면 조준으로 인정한다 — 크로스헤어를 정확히 맞추라고 요구하지 않는다 |

**이 설계의 이득 3개**
1. 헤드리스 유닛 테스트가 가능하다 — 3m 앞에 서서 `cameraYaw`만 돌려도 타겟이 바뀐다
2. 3인칭(`V`)에서도 **같은 코드**가 돈다 (아웃라인이 모드마다 다르게 굴지 않는다)
3. 드로우 콜 0, 레이캐스트 0

**벽 관통은 P1에서 허용한다.** 3m 이내에 벽을 끼고 마주 볼 상황이 이 맵에 사실상 없다(자판기·벤치·노점 전부 개방 공간). 진짜 문제가 되면 `collision.ts`에 `segmentBlocked()` 하나를 추가한다 — P2 항목으로 남긴다.

**아웃라인 렌더** (`render/props.ts`)
- 대상 프롭 하나당 `outlineMat`(`BackSide` 역폴리곤 셸) 메시 1개. **`shell.raycast = () => {}`** — `world-builder.ts:94`가 기록한 함정이다. 안 끄면 카메라 차폐 레이가 셸을 먼저 맞는다
- `uThickness` 유니폼만 쓴다: 근접 0.045 / 조준 0.068 / 거부 깜빡임 0.10 → 0
- `uInk`를 `PALETTE.gold`로. **조건·종류에 따른 색 분기 코드를 넣지 않는다** (GDD §5.1 · OBJECT-MANIFEST §"셰이더는 1개면 끝난다")
- 셸은 **현재 타겟 1개만** 켠다 → 드로우 콜 +1 상한

**입력 확장** (`core/input.ts`)
```ts
pressInteract: boolean   // 원샷. pressStart 패턴 그대로 (keydown에서 set, sample에서 소비)
pressSlot: 0 | 1 | 2 | 3 // 0 = 없음. Digit1~3 원샷
pressCancel: boolean     // ESC — 단, ESC는 포인터 락도 푼다. keydown을 같이 받는다
qteDelta: number         // 이번 프레임 마우스 x 델타 원본(px). QTE 전용
```
`KeyE`는 `MOVE_KEYS`에 없어서 `preventDefault`가 안 걸린다 → 브라우저 기본 동작 없음(안전). `Digit1~3`도 동일.
**락 중 좌클릭 = E** 는 `pointerdown`에서 `locked === true`일 때만 `pressInteract`를 세운다.

### 3.2 F-P1-03 자판기 QTE — 리듬 판정을 순수 함수로

```
   E ─► QTE_BEGIN ─► 시선 적용 정지 (락 유지) ─► 매 틱 qteSystem
                                                    │
   travel += |qteDelta|                             │
   방향 뒤집힘(sign(qteDelta) !== dir) && travel ≥ QTE.strokeTravel
                                                    │
                                            ┌───────┴────────┐
                              판정창 안(±0.18s)            창 밖
                                    │                        │
                             strokes += 1              misses += 1
                                    │                        │
                            strokes === 3 ─► 성공      misses === 3 ─► 실패(−5s)
```

| 상수 | 값 | 근거 |
|---|---:|---|
| `QTE.strokeTravel` | 220 (px) | 1600px 화면에서 화면폭 1/7. 손목만으로 왕복 가능 |
| `QTE.beatMs` | 550 | 사람이 편하게 반복하는 왕복 주기(≈1.8Hz). 헤드밥 1.35Hz보다 살짝 빠르게 |
| `QTE.windowMs` | ±180 | 550의 1/3. 너무 좁으면 마우스 감도 차이로 불공정해진다 |
| `QTE.maxMisses` | 3 | 3연속 아니고 **누적** 3 — 관대하게 |
| `QTE.timeoutMs` | 6000 | 물고 늘어지는 것 방지. 초과 = 실패 |
| `QTE.failPenaltyMs` | 5000 | GDD §5.4 "실패 시 −5s" |

**동전 시드**: `makeRng(seed ^ vendorHash)` → `pick([0, 500, 1000, 1500])`. **자판기별 독립**이고 **시드 고정**이라, 같은 시드에서 몇 번 재도전해도 같은 금액이 나온다 → *"긁는 실력"과 "운"을 분리한다.* (매번 다시 굴리면 실패 후 재시도가 도박이 되고, QTE 실력이 무의미해진다)

### 3.3 F-P1-04 단소 추격 — 상태 기계 + 같은 충돌 해석기

```
        idle ──(절도)──► draw(600ms) ──► chase ──(dist ≤ 1.2 && cd = 0)──► swing(320ms)
                                          ▲                                    │
                                          └────────── cd 1500ms ───────────────┘
                                          │
                     (Z3 진입 · 30s 경과 · 효자손 반납) ──► recover ──► return ──► idle
                                          │
                               (hitCount = 5) ──► seize(2000ms) ──► return
```

- **NPC 위치를 상태에 넣는다.** `chase.pos: Vec2` · `chase.facing` · `chase.state` · `chase.stateMs`.
  P0의 `chase`는 4필드(active/remainingMs/hitCount/swingCooldownMs)뿐이라 **위치가 없었다** — 추격이 구현 안 된 진짜 이유가 이거다
- 이동: `resolveMove(from, to, z, radius=0.32)` — **플레이어와 같은 함수.** 기둥 슬라이딩이 공짜로 따라온다
- 끼임 탈출: 3초 이상 실이동 < 0.05m/틱이면 `stuckMs` 누적 → 1.5m 후퇴 후 재접근 (텔레포트 금지 — 화면에서 순간이동하는 노인은 슬랩스틱이 아니라 공포다)
- 몸통 솔리드: `rebuildDynamics`에 `chaseSolid(s)` 추가. 높이 1.7m(점프 상한 0.55m보다 훨씬 높다 → 뛰어넘기 불가)
- 타격: `boxHitsCircle` 대신 단순 원-원 거리. `systems/roadHazard.ts`(25줄 순수 함수 + 유닛 테스트)가 선례다

**감속 회복이 상태에 있는 이유**: `speedPenalty`는 이미 `movement.ts:91`에서 `speed * (1 - speedPenalty)`로 **소비되고 있다**. 쓰는 곳은 있고 **쓰는 사람이 없었다.** P1은 writer만 붙인다.
⚠ 상한 클램프를 리듀서에 넣는다 — 1.0을 넘으면 속도가 음수가 되어 **조작이 반대로 된다.**

### 3.4 F-P1-05 인파 — 하나는 솔리드, 하나는 시간의 함수

**O-03 (에스컬레이터 인파벽)**: 상태 최소화. `consumed`에 `'CP-01'`이 들어가면 비켜선 것이다.
```ts
export const crowdSolids = (s: GameState): Solid[] =>
  s.act.consumed.includes('CP-01') ? [] : [CP_BLOCK]     // x 96.2~97.0 · y 1.35~2.45 · h 1.7
```
에스컬레이터 폭 1.7m(y 1.35~3.05) 중 **1.1m를 막는다.** 남은 0.6m는 플레이어 지름 0.64m보다 좁다 → 못 지난다. 좌측통행 위반 고증이 그대로 물리가 된다.

**O-04 (하차 역류)**: `trainAt`과 **같은 방식** — 시간의 순수 함수.
```ts
export const surgeAt = (elapsedMs: number, seed: number): SurgePhase => {
  const at = SURGE.baseMs + jitter(seed)          // 150_000 ± 8_000
  if (t < at - SURGE.warnMs) return 'idle'        // warn 3000
  if (t < at) return 'warn'                       // 안내음 + 북측 붉은 경고
  if (t < at + SURGE.durMs) return 'active'       // 6000
  return 'done'
}
```
`active` 중 승강장(z ≈ B2, y > 1.5)에 있으면 −y 방향 3.2m/s. 마스크 착용 시 ×0.5. 넘어짐은 시드 결정(30%) — `Math.random()` 금지, 재현성이 테스트의 전제다.

### 3.5 F-P1-06/07 채점과 엔딩 — 조건식은 단일 비교만

```ts
{ id: 'E-14', priority: 90, when: (s) => s.boarded && s.tally.coinsEarned >= 3000 }
{ id: 'E-10', priority: 80, when: (s) => s.scores.conscience <= -3 }
{ id: 'E-04', priority: 40, when: (s) => s.boarded && s.timeLeftMs <= 1000 }
{ id: 'E-02', priority: 30, when: (s) => s.boarded && s.timeLeftMs >= 30_000 }
{ id: 'E-01', priority: 10, when: (s) => s.boarded }
{ id: 'E-06', priority: 0,  when: () => true }
```
- `resolveEnding`은 매 호출마다 `.sort()`를 한다(`endings.ts:49`). 6종이면 무해하지만 **엔딩 화면이 매 프레임 호출한다** → 배열을 모듈 로드 시 1회 정렬해 상수로 둔다
- `screens.ts:78`은 `EndingDef.hint`를 **무시하고** `pickHint(seed)`를 쓴다. P1은 엔딩별 힌트가 필요하므로 `e.hint ?? pickHint(s.seed)`로 고친다
- `screens.sync`의 메모 키는 `phase:endingId:seed`다(`screens.ts:99`). 엔딩 화면에 점수를 찍으려면 키에 `conscience`·`coinsEarned`를 더한다

### 3.6 SFX — 절차 생성 4종

| 소리 | 합성 | 트리거 |
|---|---|---|

### 8.2 구현 중 드러난 설계 결함 5건

계획서에 없던 것들이다. **다르게 간 이유까지** 남긴다 (P0 §10.4의 형식).

#### 결함 1 — 첫 `E` 가 통째로 씹혔다

`interactSystem` 이 `s.act.targetId` 를 읽어 상호작용을 시작했다. 그런데 그 필드는
**이번 프레임에 발행한 `ACT_TARGET` 이 리듀서를 통과한 다음 프레임에나** 채워진다.
대상 앞에 서서 처음 누르는 `E` 가 항상 무시됐고, S8-4/5/7이 한꺼번에 빨간불이 됐다.
→ 이번 프레임에 계산한 `aim.id` 를 쓴다. **상태는 렌더용 캐시이고 판정용 입력이 아니다.**

#### 결함 2 — 할아버지가 벤치 솔리드 안에 있었다

`ACT-02-BENCH` 는 `at(42, 15, 2.4, 0.8)` = rect[40.8, 14.6, 43.2, 15.4] 이고
상호작용 좌표(42, 14.9)는 **그 안**이다. 앉아 있으니 당연한데, 추격이 시작되면
`resolveMove` 가 "목적지가 솔리드와 겹치면 거부"라 **20초 추격에서 이동 0.0m** 였다.
→ `standPos()` (벤치 남쪽 1.1m)를 분리했다. 일어서면 한 발 나오는 게 물리적으로도 맞다.

#### 결함 3 — 추격자가 플레이어를 3.6m 밀어냈다

몸통 솔리드(반경 0.34)가 플레이어(0.32)와 겹치면 `depenetrate` 가 플레이어를 밀어낸다.
할아버지가 계속 접근하니 매 프레임 밀었다.
→ **타격 거리(1.2m)에서 접근을 멈춘다.** 0.66m 에서만 겹치므로 1.2m 정지면 구조적으로 불가능해진다.
밀어내기는 O-04 역류 전용으로 남겼다.

#### 결함 4 — 넘어져 있는 동안 계속 미끄러졌다

역류 정지(1.2s)를 `s.player.pos` 로 "고정"했는데, 그 값은 이미 `movementSystem` 이
갱신한 것이라 매 프레임 **새 위치로 고정**됐다. 0.5초에 0.54m 밀렸다.
→ `gateKnockback` 처럼 **이동 전 상태(`prev`)** 를 받아 그 좌표로 고정한다.

#### 결함 5 ★ — 잔액 0원 시드에서 진짜 소프트락이 나왔다

스윕이 잡았다. 시작 잔액 0원(15%) + 자판기가 `0·500·500` → 세 대를 다 긁어도 1,000원이라
요금 1,400원을 **절대** 못 만든다. GDD §11은 충전 루트를 4개 두라고 했지만 P1에는 자판기만 있다.
게다가 효자손을 회수당하면(5대 피격) 마지막 수단조차 사라졌다.

→ 두 겹으로 막았다.
1. `coinPlan(seed)` 가 **3대 합계 ≥ 요금을 보장**한다. 부족분은 최다 자판기 한 대에 몰아준다
   (셋에 흩뿌리면 "세 대를 다 긁어야 겨우 요금"이 되어 강제 노동이 된다)
2. **효자손을 회수·반납당하면 할아버지가 `consumed` 에서 빠진다** — 정직한 루트로 재도전 가능.
   훔치기 분기만 `CHASE_DONE` 이 막는다(*"이번엔 꽉 쥐고 있다"*). GDD §6.2 *"벌은 주되 문은 닫지 않는다"* 그대로다.

> **이 결함은 유닛 테스트로는 절대 안 나왔다.** 시드 200개를 끝까지 걸어 보는 장치가 있어야
> 보인다. P0 §6.2가 "헤드리스 시뮬이 이 프로젝트의 핵심 테스트 장치"라고 쓴 이유가 여기서 회수됐다.

### 8.2.1 코드 리뷰에서 닫은 잠재 결함 (CRITICAL 0 · HIGH 0)

리뷰는 통과했지만 **지금은 증상이 없고 P2에서 터질 것** 두 건을 같이 닫았다.

1. **`chase.step()` 이 인파벽을 떨어뜨렸다.** 자기 몸통을 빼려고 동적 솔리드를
   `[gateFlaps, psdDoors]` 로 다시 깔았는데, 거기서 `crowdSolids`(O-03 인파벽)까지 사라졌다.
   이 틱의 남은 시스템 중 지금은 아무도 `resolveMove` 를 안 부르므로 무증상이지만,
   충돌을 보는 시스템이 추격 **뒤에** 하나 붙는 순간 그 시스템만 한 틱 동안 *벽이 없는 세계*를 본다.
   → 자기 몸통만 빼고 나머지를 전부 깐다.
2. **`itemDef()` 가 시스템 hot path 에서 예외를 던졌다.** 슬롯 사용(`useSlot`)과 HUD 렌더가
   매 입력·매 프레임 부르는 자리다. P2에서 테이블에 `gives: 'I-05'` 를 먼저 넣고 정의를
   나중에 쓰면 `tick()` 안에서 throw 되고, 파이프라인에 try/catch 가 없으니 게임이 통째로 멈춘다.
   → 던지지 않고 **자리표시자**(이름 자리에 ID, 글리프 `?`)를 돌려준다. 정의 누락이 화면에 드러난다.

부수 정리: 미발행 액션 `DROP_TAKE` 제거 · `inventory` 초기화를 `SLOTS` 에서 파생 ·
`GRANDPA_HELPED` 가 P2(E-12 조건)용 예약임을 타입에 명기.

## 9. UI 킷 — `/uikit.html`

P1 UI를 게임 밖에서 다듬기 위한 작업대. 별도 레포·별도 프로젝트로 떼지 **않았다.**

### 9.1 단일 원천으로 만든 것

| 이전 | 이후 | 읽는 곳 |
|---|---|---|
| `ui/hud.ts` 안의 CSS 템플릿 문자열 | `src/ui/css/hud.css` | 게임(`?inline`) · 킷 |
| `ui/dialog.ts` 안의 CSS | `src/ui/css/dialog.css` | 게임(`?inline`) · 킷 |
| `ui/screens.ts` 안의 CSS | `src/ui/css/screens.css` | 게임(`?inline`) · 킷 |
| `index.html` 인라인 `:root` 토큰 | `src/ui/css/tokens.css` | 게임(`<link>`) · 킷(`<link>`) |

`?inline` 을 쓴 이유: 파일 내용을 **문자열로** 받아 예전처럼 `<style>` 로 주입한다.
주입 경로가 바뀌지 않으므로 순서·범위 문제가 생기지 않고, 그러면서 파일은 킷이 읽을 수 있다.

> **토큰 이중화 주의** — `--gold` (#FFC83D)는 3D 아웃라인 색과 같은 값이고, 그쪽은
> `data/tuning.ts PALETTE.gold` 가 들고 있다. **골드를 바꾸려면 두 곳을 같이 고쳐야 한다.**
> CSS 변수를 런타임에 읽어 three.js 재질에 넣는 방법도 있지만, 렌더가 DOM 을 읽게 되므로
> 아키텍처 철칙(렌더는 상태만 읽는다)과 맞바꿔야 한다 — 색 하나 때문에 할 거래가 아니다.

### 9.2 킷이 UI를 다시 만들지 않는다

킷은 `createHud` · `createDialog` 를 **그대로 부른다.** 마크업을 베끼지 않는다 —
베끼면 UI를 고칠 때마다 두 곳을 고쳐야 하고, 그건 반드시 갈라진다(킷은 예쁜데 게임은 아닌 상태).

`src/uikit/presets.ts` 는 **상태만** 만든다. 각 프리셋이 `t`(초)를 받아 `GameState` 를
돌려주므로 진행링·QTE 마커·양심 발광처럼 **움직여야 판단되는 것**이 실제로 움직인다.

카드 격자가 아니라 상태 선택기인 이유: UI 스타일이 `#id` 선택자라 한 페이지에 두 인스턴스를
올리면 id 가 충돌한다. 킷 편의를 위해 게임 코드를 고치는 것은 순서가 거꾸로다.

### 9.5 claude.ai/design 업로드는 아직 안 했다

`/design-sync` 는 **React 컴포넌트 라이브러리 레포**(`dist/` + Storybook)를 올리는 파이프라인이다.
우리 UI는 vanilla DOM + CSS 문자열이라 그 형태가 아니다 — 올리려면 UI를 React 컴포넌트로
새로 만들어야 하고, 그러면 게임에 되돌릴 때 **수작업 변환**이 남는다.
디렉터 판단으로 이번에는 로컬 킷(단일 원천)을 먼저 세웠다. 업로드가 필요해지면 이 킷이
그대로 재료가 된다 — 상태 프리셋과 CSS 가 이미 분리돼 있다.

## 10. Figma HUD 디자인 적용 (node 4:4 · `game-hud-ui`)

디렉터가 Figma로 만든 HUD를 적용했다. **디자인의 시각 언어는 전부 가져오고, GDD와
충돌하는 두 가지는 우리 규칙을 지켰다.**

### 10.1 가져온 것

| 요소 | Figma 값 | 우리 적용 |
|---|---|---|
| 패널 | `rgba(11,12,16,.7)` · `1px rgba(255,255,255,.1)` · `0 8px 16px rgba(0,0,0,.7)` | `.hud-panel` 한 규칙 — 모든 위젯이 공유 |
| 강조색 | `#00F0FF` | `--accent` 신설. 의미는 **"플레이어 자신의 상태"**(스태미너·착용 슬롯) |
| 스태미너 | 원형 100px + 라벨 | 좌상단. 링은 **conic-gradient** — 값이 매 프레임 바뀌어 정적 SVG로는 불가 |
| 미니맵 | 220px 원형 + 존 배너 | 우상단. **P1은 잠김** (아래 §10.2) |
| 소지품 | 패널 + 슬롯 72px + 번호 뱃지 + 빈 placeholder 16px | 하단 중앙. **3칸** (아래 §10.2) |
| 잔액 | pill 배지 + 코인 아이콘 | 우하단. 문안은 `잔액 1,600원`, 부족 시 적색 규칙 유지 |
| 안내 | `hud-instruction` 필 | `#lockhint` 에 그대로. `ESC 해제`만 골드 |
| 아이콘 | backpack · circle-dollar-sign | **내보낸 SVG 원본**을 `src/ui/icons/*.svg` 로 두고 `?raw` 인라인 |

**예전 하단 4칸 `foot` 바는 없앴다.** Zone → 미니맵 배너, 잔액 → 우하단 배지,
스태미너 → 좌상단 원형, 소지품 → 하단 패널로 흩어졌다. 화면 하단이 열렸다.

### 10.2 디자인과 다르게 간 것 — 이유

| Figma | 우리 | 근거 |
|---|---|---|
| 슬롯 **8칸**(6 표시) | **3칸** | GDD §5.2 *"3슬롯 고정 · 슬롯 압박 자체가 선택을 만든다."* 칸을 늘리면 P1의 핵심 트레이드오프가 죽는다. 패널 폭도 칸을 따라 264px — 빈 칸으로 720을 채우면 압박이 사라진다 |
| 미니맵 상시 | **잠김 상태** | GDD: 미니맵은 노선도(I-13) 해금 = P2. 상시 켜면 "정보를 사는 게임"의 전제가 깨진다. 껍데기를 보여 주면 오히려 **P2 아이템의 가치를 광고**한다 |
| `소지금 12,500 G` | `잔액 1,600원` | 우리 통화는 교통카드 잔액이고 요금은 1,400원이다. 배지 스타일만 가져왔다 |
| 강조 앰버 `#FFB800` | **골드 `#FFC83D`** | 4% 차이. 골드는 3D 상호작용 아웃라인(`PALETTE.gold`)과 같은 값이어야 하고, *"만질 수 있는 것의 색은 하나"* 가 4%의 색차보다 중요하다 |
| 타이머·LED 없음 | **유지** | 180초가 이 게임의 심장이다. 디자인에 없으므로 **같은 패널 언어**로 다시 입혔다(상단 중앙 pill) |
| 양심 게이지 없음 | **유지** | GDD §7.2 필수. 소지품 패널 위 얇은 선, 숫자 미표시 |

### 10.3 적용 중 잡은 결함 3건

1. **원형 게이지의 숫자가 사라졌다** — `mask`는 자식까지 함께 잘라낸다. 숫자를 링 안에
   넣었더니 가운데 구멍과 같이 지워졌다. → 숫자를 링의 **형제**로 빼고 절대배치로 겹친다.
2. **대화·QTE 패널이 소지품 패널을 덮었다** — 소지품이 하단 중앙(bottom 40 · 높이 133)으로
   오면서 예전 여백(120)이 그 위에 걸쳤다. → 210px로 올려 양심 게이지 위에 세웠다.
3. **UI 킷 배경에 예전 HUD가 박혀 있었다** — 배경으로 쓴 P1 스크린샷에 구 HUD가 그대로 있어
   킷에서 HUD가 두 겹으로 보였다. 새 HUD를 판단할 수가 없다.
   → `tests/e2e/backdrop.spec.ts` 가 **`#ui` 를 숨기고** 씬만 찍는다(대합실·자판기·승강장 3장).

부수: UI 킷 무대가 좌우로 잘렸다 — `transform: scale` 은 레이아웃 박스를 줄이지 않는다.
축소된 크기를 차지하는 홀더를 넣어 실제 중앙에 놓이게 했다.
