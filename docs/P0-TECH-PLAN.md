### 1.3 월드 — Blender 씬을 쓴다 (v1.1 정정)

> **v1.0의 판단은 틀렸다.** 당시 *"`station_map.blend` = 1,028,101 폴리곤, 웹 예산 33배 초과"*라고 쓰고
> 절차 생성 그레이박스로 갔다. 컬렉션별로 다시 재보니 그 폴리곤의 **94%는 `CROWD`(940,608)** —
> P1용 군중 플레이스홀더였다. 실제 역사 지오메트리는 이렇다.

| 컬렉션 | 삼각형 |
|---|---:|
| Z1_GROUND | 16,840 |
| Z5_PLATFORM | 6,852 |
| Z4_DESCENT | 4,284 |
| Z5_TRAIN | 4,152 |
| Z2_CONCOURSE | 3,584 |
| Z3_GATES | 1,368 |
| **역사 합계** | **37,080** |

37k 삼각형은 게임이 한 화면에 그리는 양(약 25k)과 같은 자릿수다. **예산 초과가 아니라 예산 안이었다.**
총합만 보고 군중을 걸러내지 않은 한 줄 때문에, 이미 만들어 둔 에셋을 놔두고 박스를 새로 세웠다.

**진짜 제약은 폴리곤이 아니라 오브젝트 수**였다. 1,551개를 그대로 올리면 드로우 콜 1,551이다.
머티리얼별로 병합하면 존당 13~31개로 떨어진다.

#### 현재 구조 — 보이는 것과 막는 것의 분리

```
Blender 씬 ──익스포트──► 존별 GLB 6개 ──로더──► 씬 (보이는 것)
MAP 부록 A 좌표 ────────► data/world.ts ──────► 충돌·존 판정 (막는 것)
```

두 계통이 같은 좌표를 보되 **서로를 모른다.** 아트가 바뀌어도 밸런스가 안 흔들리고,
GLB 로드가 실패해도 그레이박스 폴백으로 게임은 끝까지 돌아간다.

| 항목 | 값 |
|---|---|
| 존별 GLB | 6개 · 원본 2.6 MB · **gzip 169 KB** |
| 로드 후 메시 | 1,446 → 병합 후 존당 13~31 (+ 동적 부품) |
| 텍스처 | 0개 (툰 단색이므로 익스포트에서 제외 — 이것만으로 Z1이 876→314 KB) |
| 좌표 정렬 | 보정 0 — glTF Y-up 변환이 `(x, y, z)월드 → (x, z, −y)three` 와 정확히 일치 |

캐릭터는 그대로 `mc_character_rigged.glb`를 쓴다.

## 3. 아키텍처 — 3계층 단방향

```
   ┌──────────────── 매 프레임 ────────────────┐
   │                                          │
   │  input.sample()  ──► InputFrame          │
   │                          │               │
   │                          ▼               │
   │   ┌─── 시뮬레이션 (고정 60Hz) ──────────┐  │
   │   │  systems.forEach(sys =>            │  │
   │   │     actions.push(...sys(state,ctx))│  │
   │   │  )                                 │  │
   │   │  state = actions.reduce(reducer,   │  │
   │   │                          state)    │  │
   │   └────────────────────────────────────┘  │
   │                          │                │
   │                          ▼                │
   │   ┌─── 렌더 (가변, 보간) ───────────────┐  │
   │   │  rigs.forEach(r => r.sync(state,α))│  │
   │   │  renderer.render(scene, camera)    │  │
   │   │  hud.sync(state)                   │  │
   │   └────────────────────────────────────┘  │
   └──────────────────────────────────────────┘
```

**철칙 3개**

1. **시스템은 상태를 직접 바꾸지 않는다.** 액션만 반환한다. → 모든 변경이 리듀서 한 곳을 통과하므로 로그·리플레이·시드 재현이 자동으로 성립한다.
2. **렌더는 상태를 읽기만 한다.** 렌더 코드가 게임플레이에 영향을 주면 프레임레이트가 밸런스를 바꾼다.
3. **시뮬은 고정 60Hz.** 프레임이 튀어도 물리가 안 튄다. 렌더는 α(보간계수)로 부드럽게 그린다.

### 3.1 고정 스텝 루프 — 정확히 이렇게

```ts
const STEP = 1000 / 60
let acc = 0, prev = performance.now()

function frame(now: number) {
  let dt = now - prev; prev = now
  if (dt > 250) dt = STEP            // 탭 복귀 스파이럴 차단 (기획서 F-04 성공기준)
  acc += dt
  let steps = 0
  while (acc >= STEP && steps++ < 5) { state = tick(state, STEP); acc -= STEP }
  render(state, acc / STEP)
  requestAnimationFrame(frame)
}
```

`dt > 250` 클램프가 **탭 백그라운드 후 복귀 시 타이머 점프**를 막는다. 이게 없으면 사용자가 탭을 5분 두고 오면 게임이 즉시 끝나 있다.

## 4. 핵심 기능 작동 방식

### 4.1 F-01 이동 — 카메라 상대 + 지수 감쇠

```
입력 (WASD) → 카메라 요 회전 적용 → 정규화 목표 방향
                                          │
    목표속도 = dir × (스프린트 ? 8.3 : 5.0) × (1 − speedPenalty)
                                          │
    vel = lerpExp(vel, 목표속도, dt, τ)     τ = 입력있음 0.12s / 없음 0.09s
                                          │
    다음위치 = pos + vel·dt  ──► collision.resolve() ──► 확정
                                          │
    facing = lerpAngle(facing, atan2(vel), 14 rad/s)
    z = ground.sample(x, y)     ← 층 · 램프 볼륨
```

`lerpExp(a,b,dt,τ) = b + (a−b)·exp(−dt/τ)` — **프레임레이트 독립** 지수 보간. 흔히 쓰는 `lerp(a,b,0.2)`는 60fps와 144fps에서 다르게 움직인다. 그건 버그다.

**스태미너**: 스프린트 −22/s, 회복 +14/s (마지막 스프린트 후 1.0s 지연). 0 도달 시 잠금, 30 회복해야 해제 (히스테리시스 — 없으면 0 근처에서 스프린트가 깜빡인다).

### 4.2 F-03 충돌 — AABB 슬라이딩

```
1. 다음 위치 후보 계산
2. 근처 AABB 질의 (16m 균일 그리드 해싱 — 브로드페이즈)
3. X축만 이동 → 겹치면 X 되돌림
4. Y축만 이동 → 겹치면 Y 되돌림
5. 확정
```

축별 분리 해결(separate-axis resolve)이 벽에 붙어 미끄러지는 느낌을 만든다. 동시 해결하면 모서리에서 끼인다.

**램프 볼륨** (경사): `{xy범위, z시작, z끝, 축}`. 볼륨 안이면 `z = lerp(z0, z1, 진행률)`. 계단·에스컬레이터·출구계단 3종.

**출처**: 모든 박스는 `data/world.ts`에서 부록 A 좌표로 선언. 예:
```ts
{ id:'OBJ-28-N', box:[44,6.6, 56,7.0], h:3.0 }      // Z2 가림막 북면
{ id:'GATE-G3',  box:[60.3,13.7, 61.7,14.3], h:1.2 } // 게이트 본체
```

### 4.3 F-05 개찰구 — 상태 기계

```
      ┌──────────┐   플레이어가 통로 진입 (x 59.8~60.3)
      │   IDLE   │──────────────┐
      └──────────┘              ▼
           ▲              ┌───────────┐
           │              │  TAGGING  │ 0.35s
           │              └─────┬─────┘
           │                    │ 판정
           │        ┌───────────┴───────────┐
           │   정상 & 잔액≥1400          그 외
           │        │                       │
           │        ▼                       ▼
           │  ┌──────────┐            ┌──────────┐
           │  │  OPEN    │ 플랩 개방   │ REJECT   │ 부저 · 적색
           │  │  2.0s    │ −1,400원   │ 3.0s CD  │ −8s · 1.6m 후퇴
           │  └────┬─────┘            └────┬─────┘
           │       │ x≥62                  │
           │       ▼                       │
           │  ┌──────────┐                 │
           │  │  PASSED  │ ★비가역          │
           │  └──────────┘                 │
           └───────────────────────────────┘
```

**시드**: `rng(seed).pick([1..6])`, 15% 확률로 2개. 램프 색은 이 결과의 **직접 투영**이다 — 별도 데이터가 아니라 `working.includes(id) ? GREEN : RED`. 램프가 거짓말할 구조적 가능성 자체를 없앤다.

**쿨다운 3.0s**가 무작위 대입을 막는다. 없으면 6개를 5초 만에 다 시도할 수 있고 그러면 이 게임의 유일한 판단이 사라진다.

### 4.4 F-07 열차 — 시간 구동 (Time-driven)

열차는 **플레이어와 무관하게** 시간만 보고 움직인다. 상태는 `elapsedMs`의 순수 함수다.

```ts
const trainAt = (t: number) =>
  t < 168_000 ? { s:'incoming', x: lerp(320, 78, ease(t/168_000)) , door:0 }
: t < 172_000 ? { s:'arriving', x: decel(t), door:0 }
: t < 180_000 ? { s:'open',     x: STOP,     door: min(1,(t-172_000)/1200) }
: t < 181_200 ? { s:'closing',  x: STOP,     door: 1-(t-180_000)/1200 }
: t < 182_000 ? { s:'closed',   x: STOP,     door:0 }
:               { s:'departed', x: lerp(78, -160, ...), door:0 }
```

순수 함수라서 **시간을 스크럽하면 열차가 그대로 따라온다** → 디버그에서 t=179s로 점프해 탑승 판정만 반복 테스트할 수 있다. E2E 테스트 시간이 3분에서 3초로 줄어든다.

**탑승 판정**: 문 32개소를 `x = 78 + 16k + {2,6,10,14}`로 생성. 매 틱 플레이어와 가장 가까운 문 1개만 검사(선형 탐색 32회는 무시할 비용). 조건 3개(문 상태 · 개구 사각형 내부 · +y 입력)가 전부 참이면 `BOARD` 액션.

### 4.5 F-02 카메라 — 존 프리셋 보간

```
zone 변경 감지 → 목표 {yaw, pitch, dist} = PRESET[zone]
              → 1.2s ease-in-out 보간 (컷 없음)

매 프레임:
  anchor = player.pos + vel × 0.28          선행(look-ahead)
  target = lerpExp(target, anchor, dt, 1/6.0)
  camera.pos = target + sph(yaw+userYaw, pitch+userPitch, dist×userZoom)
  camera.lookAt(target + [0,0,0.9])
```

**Z3 특례**: 프리셋 대신 `dist`를 계산한다 — y 6~26(20m)이 화면 세로 70%에 들어가는 거리. `dist = 10 / (2·tan(fov/2)·0.7) × aspectCorr`. 기획서 F-02 성공기준(램프 6개 동시 가시)을 코드로 보장한다.

### 4.6 렌더 — 툰 + 인스턴싱

- **툰**: `MeshToonMaterial` + 3단 그라디언트 램프 텍스처(4×1 DataTexture). 조명 1 directional + 1 hemisphere.
- **아웃라인**: 후면 확장(back-face expansion) — 동일 지오메트리를 `BackSide`, 법선 방향 팽창 셰이더로 한 번 더. 드로우 콜 2배지만 인스턴싱으로 상쇄.
- **인스턴싱**: 반복 오브젝트(기둥 8, 게이트 6, 안전문 32, 계단 87단, 역명판 8, 전차 8량)는 전부 `InstancedMesh`. 87단 계단을 개별 메시로 그리면 그것만으로 드로우 콜 예산을 절반 먹는다.
- **안개**: B1/B2 `FogExp2` — 존 밖 지오메트리를 자연스럽게 잘라 프러스텀 컬링을 돕고, 지하 분위기도 같이 얻는다.

## 6. 테스트 전략

### 6.1 계층

| 계층 | 도구 | 대상 | 비율 |
|---|---|---|---|
| 유닛 | Vitest | 리듀서 · 시스템 · 시드 · 좌표 | 70% |
| 통합 | Vitest (헤드리스 시뮬) | 존 주파 · 게이트 시나리오 · 열차 스케줄 | 20% |
| E2E | Playwright | 완주 · 성능 · 콘솔 · 스크린샷 | 10% |

### 6.2 헤드리스 시뮬 — 이 프로젝트의 핵심 테스트 장치

시스템이 순수 함수라서 **렌더 없이 게임 전체를 돌릴 수 있다.**

```ts
const sim = (seed: number, script: InputFrame[]) =>
  script.reduce((s, input) => tick(s, 16.67, input), initialState(seed))
```

이걸로 가능해지는 것:
- 3분 플레이를 **20ms에** 시뮬레이션 → 시드 1,000개 밸런싱 스윕이 20초
- 랜덤 입력 퍼즈로 소프트락 탐지 (A-5)
- 열차 스케줄을 t=179s로 점프해 탑승 판정만 반복 (§4.4)

**렌더를 순수 시뮬에서 분리한 진짜 이유가 이것이다.** 아키텍처 철칙 2는 미학이 아니라 테스트 속도다.

### 6.3 자동 검증 명령

```bash
npm test          # 유닛 + 통합
npm run test:e2e  # Playwright
npm run verify    # tsc --noEmit && test && build && test:e2e   ← 각 단계 종료 시
```

## 12. 1인칭 전환 (v1.2 · 2026-07-31)

쿼터뷰를 1인칭으로 바꿨다. **시점이 바뀌면 월드의 전제도 바뀐다** — 카메라 코드만 갈아끼우는 작업이 아니었다.

### 12.1 뒤집힌 전제

| 항목 | 쿼터뷰 | 1인칭 |
|---|---|---|
| 천장·지붕 | **지워야 했다** (카메라가 그 위에 서므로 화면을 통째로 막음) | **있어야 한다** (없으면 실내가 실내로 안 읽힘) |
| 플레이어 모델 | 보여야 함 | 꺼야 함 (전용 팔 메시는 P1) |
| 카메라 차폐 당김 | 필수 | 불필요 |
| 존별 카메라 프리셋 | 존마다 요/피치/거리/화각 | 자유 시선 |
| W가 가는 방향 | 존 프리셋 요에 종속 | 보는 방향 |

그래서 station 로더는 머리 위 구조물을 **지우지 않고 별도 그룹으로 분리**해 모드에 따라 켠다.
쿼터뷰(V 키)는 확인용으로 남겨 뒀고, 두 모드가 같은 지오메트리를 공유한다.

### 12.2 구현

| 항목 | 값 |
|---|---|
| 화각 | 74° (스프린트 시 +8°, 시정수 0.18s) |
| 눈높이 | 1.62 m — 맵이 실척(문 1.9m·벽 3.2m)이라 여기서 벗어나면 공간감이 깨진다 |
| 시선 | 포인터 락 (좌클릭 진입 · ESC 해제). 피치 ±83° |
| 헤드밥 | 실제 이동 속도 비례, 수직 0.045m + 좌우 0.028m. 정지 시 0.12s로 감쇠 |
| 근평면 | 0.08 (쿼터뷰 0.5) |

이동은 원래부터 카메라 상대였으므로 `cameraYaw`에 시선 요를 넣는 것으로 그대로 작동한다.
탑승 판정을 입력축이 아니라 **월드 속도**로 바꿔 둔 것(§10.4-4)이 여기서 값을 했다 — 시점을 통째로 갈았는데 판정 코드는 그대로다.

### 12.3 설계 변경 — S4-8을 폐기하고 다시 썼다

원래 기준은 *"Z3 카메라에서 게이트 램프 6개가 **동시에** 보인다"* 였다 (MAP §5.4 "정보를 전부 보여준 뒤에 선택시킨다").

**1인칭에서는 물리적으로 불가능하다.** 게이트 6기는 y 6~26으로 20m에 걸쳐 있고,
진입선(x=56)에서 게이트(x=60.3)까지 4.3m다. 전부 담으려면 화각 140°가 필요하다.
9m 뒤로 물러나면 각도는 되지만 그 지점은 Z2이고 벽 개구부(y9~19)가 G1·G6을 가린다.

새 기준: **"고개를 돌리면 전부 판독되고, 정면에서 최소 2기는 동시에 보인다."**

이건 후퇴가 아니라 **GDD §1.2에 더 맞는다** — *"이 게임은 달리기 게임이 아니라 관찰하고 판단하는 게임이다."*
쿼터뷰는 정보를 공짜로 줬지만, 1인칭은 **정보에 시간이라는 값을 매긴다.** 이 게임의 유일한 화폐가 시간이므로 그게 옳다.
다만 이건 디렉터 판단 사항이라 P0-SPEC §2.5의 단서 표와 함께 검토가 필요하다.

### 12.4 표지판 판독 — 세 번 실패하고 고친 것

게이트 ▲/✕ 기호를 사인 앞에 띄우는 데 세 번 실패했다.

1. **고정 −x 오프셋** → 사인이 아래로 기울어져 있어 프레임에 파묻힘
2. **사인 면 법선 방향 오프셋** → 법선 추정이 빗나가 여전히 파묻힘
3. **카메라 방향 빌보드** → 앞으로 나왔지만 기호 색이 배경과 같아 안 보임
4. **흰색 기호 + 월드업 고정 `lookAt`** → 해결

교훈 둘. **기하 추정보다 카메라 기준 빌보드가 각도와 무관하게 확실하다.**
그리고 **색은 배경과 분리해야 형태가 정보가 된다** — 색각 대응의 핵심은 색이 아니라 대비다.

사인 자체도 `MeshStandardMaterial`에서 자체발광 `MeshBasicMaterial`로 바꿨다.
조명·톤매핑을 거치면 지정한 초록이 화면에서 살구색으로 나왔다.
**이 색이 이 게임의 유일한 판단 근거**라 정확해야 한다.

## 13. Blender 씬 결함 처리 (v1.3 · 2026-07-31)

§11.3에 적은 결함 4건을 실제로 손봤다. **그 과정에서 1건은 내 오진이었음이 드러났다.**

### 13.1 결과

| # | §11.3 당시 판단 | 실제 | 조치 |
|---|---|---|---|
| 1 | Z1·Z2·Z3 전체 `hide_render` | **맞음** — 지난 세션 렌더 연출 상태 | 씬에서 448개 해제 후 저장 |
| 2 | Z1 28개 스케일 버그 (실측 5.2 km) | **틀림 — 오진.** 전부 정상이었다 | 씬은 원복, **익스포트 필터를 고침** |
| 3 | Z1 보도 슬랩 없음 | **맞음** — `SW_PAVER`가 연석 하나에만 | `Z1_sidewalk_W/E` 신설 (SW_PAVER) |
| 4 | 버스 2개 (8버텍스 잔재 + 실물) | **맞음** | 익스포트에서 이름으로 제외 |

게임 쪽 우회 코드(`buildFloorPatches`)는 씬이 고쳐졌으므로 제거했다.
**4번 출구와 붕어빵 노점이 돌아왔다** — 오진 때문에 빠져 있던 것들이다.

### 13.2 오진의 정체 — 크기를 세 소스가 다르게 보고한다

`o.dimensions`가 출입구를 5,207 로 보고했다. 부록 A는 9.8 m다. 1000배 차이 → "스케일 버그"로 판단했다.

**틀렸다.** 스케일이 극단적으로 작으면(`1e-3` 이하) `o.dimensions`·`o.matrix_world`·`o.bound_box`가
전부 **스케일을 뺀 로컬 익스텐트**를 돌려준다. `matrix_world.to_scale()`이 `1.0`을 반환하는 것까지 확인했다 —
파일을 새로 열어도 그렇다.

캐시를 우회하는 유일한 계산:

```python
size = (max(v.co.x) - min(v.co.x)) * abs(o.scale.x)   # 로컬 정점 × 오브젝트 스케일
```

이 식으로 재니 출입구는 로컬 5,207.4 × 스케일 0.001 = **5.21 m**,
90° 요를 반영하면 월드 x 9.79 · y 5.21 · z 7.79 — **부록 A(9.8 / 5.2 / 7.79)와 정확히 일치**했다.
붕어빵 13.4 cm · 어묵 꼬치 22.6 cm · 호떡 10.1 cm. 전부 실물 치수였다.

익스포트 필터를 `o.dimensions <= 150` 에서 이 식으로 바꿨다. Z1 대상이 124 → 153개가 됐다.

### 13.3 이 오진이 가능했던 이유

§11.3을 쓸 때 **크기를 한 소스로만 확인하고 끝냈다.** 5,207이라는 숫자가
"1000배 유닛 미스매치"라는 그럴듯한 서사에 맞아떨어져서 교차 검증을 안 했다.

## 14. 저더 제거 · 점프 (v1.4 · 2026-07-31)

### 14.1 화면 덜컹거림 — 렌더 보간을 빠뜨렸다

§3.1에 *"렌더는 α(보간계수)로 부드럽게 그린다"* 라고 써놓고 **구현을 안 했다.**
시뮬은 고정 60Hz인데 카메라가 그 계단식 위치를 그대로 썼다.

프레임이 60Hz보다 **빠르면** 시뮬 스텝이 0회인 프레임이 섞인다. 그 프레임은 이전과 똑같은 위치를 그리고,
다음 프레임에서 한 스텝만큼 튄다. 멈췄다 튀었다를 반복하는 게 눈에 보이는 덜컹거림이다.

```ts
const alpha = Math.min(1, acc / STEP_MS)
renderPos = lerp(prevStepPos, currentStepPos, alpha)
```

카메라와 캐릭터 모델 모두 이 위치를 쓴다.

**계측 (`tests/unit/interp.test.ts`)** — 프레임간 이동량의 변동계수:

| 프레임레이트 | 보간 OFF | 보간 ON |
|---|---:|---:|
| 144 Hz | 1.189 | **0.000** |
| 120 Hz | 0.996 | **0.000** |
| 90 Hz | 0.709 | **0.000** |

> E2E로 재려다 실패했다. **헤드리스는 소프트웨어 렌더러라 항상 60Hz보다 느려서 0스텝 프레임이 안 생긴다.**
> 보간을 껐다 켜도 수치가 똑같이 나왔다 — 관측할 수 없는 환경에서 통과하는 테스트는 거짓 안심이다.
> 그래서 루프 수식만 떼어내 결정론적 유닛 테스트로 옮겼다.

### 14.2 헤드밥이 9.2 Hz였다

```
bobPhase += speed × 1.85 × π      // 5 m/s에서 29 rad/s
bobY = sin(bobPhase × 2)          // → 9.2 Hz
```

사람 보행은 걸음당 약 2 Hz다. 걷는 게 아니라 떨고 있었다.
게다가 위상을 **속도로** 굴려서 프레임 dt 흔들림이 그대로 위상 지터가 됐다.

**시간 기준 케이던스로 재작성**: `1.35 + 0.13 × 속도` Hz (걷기 2.0 Hz · 스프린트 2.4 Hz),
진폭 0.045 → 0.024 m, 좌우 흔들림은 수직의 절반 주기.

### 14.3 점프

Blender의 `Jump` 클립(36프레임)은 이미 제대로 된 것이었다 —
웅크림(f6) → 도약(f12) → 공중 턱(f20) → 착지 준비(f28) → 착지(f36).
`Root.location.z`가 전부 0인 **제자리 클립**이라 코드 구동 점프에 그대로 맞는다.

문제는 하나. 웅크림 0.2초를 먼저 재생하면 **입력 지연**이 된다.
그래서 구간을 잘라 두 클립을 새로 만들었다.

| 클립 | Jump 원본 구간 | 길이 | 용도 |
|---|---|---:|---|
| `JumpAir` | f12~28 | 0.53 s | 도약 순간부터 재생. 실제 체공시간(0.51 s)과 거의 일치 |
| `JumpLand` | f28~36 | 0.27 s | 착지 |

> 익스포터가 새 액션을 무시했다. 원인은 `action.id_root`가 비어 있어서 —
> `'OBJECT'`로 지정해야 나간다. 같은 필드를 이용해 AJ/GP 액션을 임시로 가려
> MC GLB에 남의 애니가 딸려 나가는 것도 막았다 (796 → 619 KB).

**물리 파라미터 — 레벨을 깨뜨리지 않는 선**

| 항목 | 값 | 근거 |
|---|---:|---|
| 초기 속도 | 4.3 m/s | |
| 중력 | 17 m/s² | 실제(9.8)보다 무겁게. 체공이 길면 3분 게임에서 답답하다 |
| **정점 높이** | **0.54 m** | ★ 충돌은 높이 기반이라 정점이 장애물 높이를 넘으면 통과해버린다 |
| 코요테 타임 | 110 ms | 계단 모서리에서 한 프레임 늦게 눌러도 받아준다 |
| 입력 버퍼 | 130 ms | 착지 직전에 누른 점프를 착지 순간에 살린다 |
| 스태미너 | 6 | |

정점 0.54 m는 **이면도로 차단(1.1 m)·개찰구 플랩(1.15 m)의 절반 아래**다.
그래서 신호등을 뛰어넘거나 개찰구를 도약해 넘는 일이 생기지 않는다.
(GDD E-09 "개찰구 도약"은 역무원 시야(P2)가 들어와야 성립하는 루트다)

유닛 테스트가 이 두 가지를 직접 막는다 —
*"개찰구 플랩을 뛰어넘을 수 없다"* · *"적신호 차단을 뛰어넘을 수 없다"*.

**GDD 충돌**: §7.1이 `Space`를 슬라이딩(스크린도어 돌파)에 배정해 뒀다.
P0에는 슬라이딩이 없어 `Space` = 점프로 뒀다. P1에서 슬라이딩이 들어오면
문 앞에서만 슬라이딩, 그 외엔 점프로 문맥 분기하거나 키를 나눠야 한다.

## 15. 마우스 스킵 · 계단/출입구 재건 · 맵 품질 상향

### 15.1 마우스 "스킵" — 원인이 넷이었다

포인터 락 시선이 간헐적으로 순간이동하는 증상. 하나의 버그가 아니라 서로 다른 네 가지가
같은 증상으로 보이고 있었다. `src/core/look.ts`에 순수 함수로 분리해 각각을 개별 테스트한다.

| # | 원인 | 처치 | 검증 |
|---|---|---|---|
| 1 | 락 성립 순간 커서가 화면 중앙으로 워프하고 그 이동량이 첫 `mousemove`에 실린다 | 락 후 80 ms 델타 폐기 | 유닛 |
| 2 | 포커스 전환·드라이버 폴링 누락이 한 이벤트에 수백 px을 몰아준다 | 절대 임계(260 px) + 직전 대비 배율(6배) 스파이크 판정 | 유닛 |
| 3 | 프레임 히치(GC·텍스처 업로드)로 한 프레임에 이동량이 몰린다 | 최근 방출 속도의 3배까지만 내보내고 나머지는 이월(총량 보존) | 유닛 |
| 4 | OS 마우스 가속 — 같은 물리 이동이 손 속도에 따라 다른 회전량이 된다 | `requestPointerLock({ unadjustedMovement: true })` | — |

또한 락 중 시선을 `pointermove` → **`mousemove`** 로 옮겼다. 포인터 락 명세가 기준으로 삼는
이벤트가 `mousemove`이고, Chrome의 `PointerEvent.movementX`는 락 상태에서 오래 문제가 있었다.
오빗 드래그(3인칭)만 `pointermove`에 남는다.

**설계에서 일부러 뺀 것** — 프레임당 이동량을 균등화하는 상시 평활화. rAF와 폴링 위상이
어긋나 생기는 0/2배 교대까지 잡아 주지만, 대가로 모든 조준에 한 프레임 지연이 붙는다.
증상은 "간혹" 튄다는 것이었고, 상시 현상이 아닌 것에 상시 비용을 치를 이유가 없다.

**테스트 경계 — 무엇을 어디서 재는가**

E2E(`tests/e2e/look.spec.ts`)는 **배선만** 검증한다. 포인터 락이 걸리는지, `mousemove`가
실제로 카메라를 돌리는지, 손을 떼면 멈추는지. 스파이크 억제는 여기서 재지 않는다 —
계측해 보니 락 상태에서 Playwright의 `mouse.move`가 요청량을 전달하지 못한다.
200 px을 요청하면 약 40 px만 들어오고, 900 px은 이벤트 자체가 발생하지 않았다(`jump=0.0000`).
필터 상수를 무력화(`SPIKE_ABS=999999`)하고 돌려도 그대로 통과했다.
**필터를 꺼도 통과하는 단언은 보증이 아니라 착각이다.** 그래서 스파이크·히치는 현상을
재현할 수 있는 유닛 테스트에 두고, E2E는 잴 수 있는 범위로 좁혔다.

### 15.2 계단과 출입구 — 상자였던 것을 계단으로

`Z1toZ2_stair`는 **정점 8개짜리 6×8×6 상자**였다. 계단이 아니라 그냥 덩어리다.
출입구는 개구부만 있고 사인·캐노피가 전무했으며, 점자블록은 계단실 밖(y 24.4)에 있었다.

치수는 도시철도 정거장 설계지침(표준 단너비 330 × 단높이 165)에서 잡았다.
12.6 m 안에 6 m를 넣어야 하므로 **단너비 325 · 단높이 6/35(≈171)** 가 한계 조합이다.
건축법이 요구하는 3 m 상승마다의 계단참을 1.2 m로 넣어 18단 + 계단참 + 17단이 됐다.

**여기서 배운 것 — 보이는 것과 밟는 것이 갈리면 안 된다.**
처음엔 충돌을 기존 직선 램프로 두고 시각만 계단참을 넣었다. 최대 **0.30 m** 어긋나
발이 디딤판을 뚫었다. `ENTRANCE_RAMP`를 램프A + 계단참 Slab + 램프B로 쪼개
Blender 지오메트리와 **같은 상수**에서 좌표가 나오도록 고쳤다.

### 15.3 진단 도구 — 눈으로 보고 헛짚지 않기

계단이 안 보이는 원인을 **세 번 연속 잘못 짚었다.** 하부 슬래브 탓이라고 고쳤지만
그림이 그대로였고, 브라우저 캐시 탓이라고 의심했지만 강제 리로드해도 그대로였다.

그래서 화면 중앙에 실제로 무엇이 있는지 이름으로 읽는 훅을 넣었다 —
`window.__game.pick(ndcX, ndcY)`. 한 번 쏘자 답이 바로 나왔다:

- `merged:ST_CEIL` @ (11.44, 28, −2.50) → **Z2 대합실 천장**에 계단실 개구부가 없었다
- `merged:MAT_ENTR`, `merged:SW_PAVER` @ z≈0 → **출입구 건물 바닥과 인도**가 계단 위를 덮고 있었다
- 서쪽 면이 z 1.0~3.0에서 막혀 있어 **개구부 높이가 1 m뿐**이었다 (충돌은 열려 있었다)

세 군데 모두 수직 개구부를 뚫어 해결했다. 규칙으로 남긴다 —
**"저 흰 면이 뭐지"에서 두 번 이상 헛짚으면 추측을 멈추고 이름을 읽는다.**

순회 촬영(`tests/e2e/tour.spec.ts`)도 같은 목적의 계측기다. 17개 고정 지점에서 1인칭
스크린샷을 남긴다. 초기 버전은 z를 손으로 적었다가 실제 지면과 어긋난 높이에서 찍혀
"지오메트리가 이상하다"는 잘못된 결론을 냈다. 지금은 살짝 띄워 낙하시켜 접지시킨 뒤
**게임이 정한 z를 되읽어 로그로 남긴다.**

### 15.4 맵 품질 — 실사 계측 기반

Wikimedia Commons의 신도림역 2호선 승강장 실사에서 인물(1.72 m)을 기준으로 픽셀 계측했다.

| 관찰 | 계측값 | 적용 |
|---|---|---|
| 기둥 | 원형 Ø≈1.1 m, 흰 사각타일, 하부 짙은 스커트 | Z2 9본 · Z5 15본을 16각 원기둥으로 교체 (기존 1.0×1.0 각기둥) |

이 밖에 격자 천장 리브 + 연속 라인 조명 + 원형 덕트, 승강장 벽면 광고 패널,

툰 셰이딩이 3단 램프라 곡면이 밴딩으로 또렷하게 읽힌다 — 원기둥·베벨의 효과가 크다.

**유리를 유리로** — 안전문·에스컬레이터 난간·상가 창이 불투명이었다. 반투명(0.34)으로
바꾸고 `renderOrder = 2`를 줬다. 미관 문제가 아니다: **안전문 너머로 들어오는 열차를
보는 것이 이 게임에서 정보다.**

### 15.6 익스포트 재현성과 용량

익스포트가 스크립트로 남아 있지 않아 **어떤 오브젝트가 왜 빠졌는지 추적할 수 없었다**
(과거 "출입구가 사라진" 사고의 배경). `tools/export_station.py`로 규칙을 못박았다.
오브젝트 삭제는 Blender를 죽이므로 **삭제 대신 `xx_` 접두어로 개명해 격리**한다.

용량은 계측으로 잡았다. Z5_PLATFORM 기준:

| 조건 | 크기 |
|---|---:|
| 기본(`resolution_u=12`) | 4,378 KB |
| `=2` | 1,485 KB |
| FONT 제외 | 510 KB |

**용량의 88 %가 글자였다.** 게임은 텍스처를 쓰지 않아 글자가 실루엣으로만 읽히므로
곡선을 세밀히 쪼갤 이유가 없다 — `TEXT_RESOLUTION = 1`로 고정했다.
베벨도 처음엔 2 세그먼트로 걸어 총량이 6.7 MB까지 갔다. 1 세그먼트로 낮추고
열차(바깥면만 잠깐 보인다)에서는 제거해 4.4 MB로 정리했다.

## 16. 플레이 피드백 반영 — 입구 시야 · 깜빡임 · 동선 안내

### 16.1 "역 입구가 막힌 것처럼 보인다"

충돌은 열려 있는데 시각이 벽이었다. `pick()`으로 재 보니 접근 지점 어디에서든
눈높이 광선이 **같은 좌표(x 4.05, z 1.62)에서 `merged:ST_CEIL`에 맞았다.**

경사 소핏을 계단 코 라인 바로 위(2.7 m)부터 시작한 게 원인이다. 계단이 27.8°로
내려가므로 문에서 2 m만 지나면 천장이 눈높이까지 내려온다 — 안을 볼 수가 없다.

실제 출입구 헤드하우스는 상부 계단참과 첫 몇 단 위가 **평천장으로 트여 있고**,
경사 소핏은 안쪽으로 들어가서 시작한다. 그대로 고쳤다 —
x −1.3 ~ 5.6 평천장(z 3.05), 그 뒤부터 계단과 나란히 하강.
이제 문 밖에서 계단이 내려가는 게 보인다.

**같이 드러난 것**: 인도의 점자 유도선이 입구를 **지나쳐** 계속 동쪽으로 가고 있었다.
선을 따라가면 출입구 측벽 앞에서 막힌다. 입구로 꺾는 분기와 방향전환 경고블록을 넣었다.

### 16.2 바닥·벽이 움직일 때 점멸

전형적인 Z-파이팅. 원인은 하나가 아니라 **내가 추가한 데칼 전부**였다 —
줄눈·점자블록·노선띠·광고판이 호스트 표면과 **정확히 같은 높이에서 시작**하고 있었다
(바닥 z = −6.00 / −20.00, 벽 y = 0.00). 상자의 뒷면이 호스트 면과 동일평면이면
카메라가 움직일 때마다 어느 쪽이 앞인지 뒤집힌다.

두 겹으로 막았다.
1. **지오메트리** — 바닥 데칼을 6 mm 띄웠다.
2. **폴리곤 오프셋** — 데칼 머티리얼에 `polygonOffset(-2,-2)`. 원거리에서는 깊이
   정밀도가 6 mm를 못 버티기 때문에 기하 오프셋만으로는 부족하다.

머티리얼 이름으로 데칼을 판별하므로(`DECAL_MATERIALS`) 앞으로 추가하는 바닥/벽
표시물은 그 집합에 이름만 넣으면 된다.

### 16.3 유도선 · 흐르는 화살표

유도블록은 "여기가 길이다"는 말하지만 **어느 쪽인지**는 말하지 않는다.
3분짜리 게임에서 길을 되짚는 시간이 가장 아깝다 — 방향을 움직임으로 준다.

- 유도(선형)블록 폭 0.6 → **0.35 m**. 0.6은 화면에서 도로 차선처럼 굵었다.
  경고(점형)블록은 원래 넓은 게 맞으니 그대로 뒀다.
- `render/guide-arrows.ts` — 셰브런을 InstancedMesh 하나로 묶어 경로를 따라 흘린다.
  텍스처 스크롤이 아니라 지오메트리를 실제로 옮긴다(이 게임은 텍스처를 안 쓴다).
  경로는 `data/world.ts`의 `GUIDE_PATHS`가 단일 원천이고 Blender 지오메트리와 같은 좌표다.

색은 **바탕보다 짙게** 잡았다. 노란 블록 위에 더 밝은 걸 얹으면 형태가 안 읽힌다 —
색이 아니라 대비가 정보를 만든다.

주의: 인스턴스 스케일을 0으로 만들어도 메시 자체는 드로우 콜을 먹는다.
근처에 하나도 없으면 `mesh.visible = false`로 아예 끈다.

### 16.4 버스가 통째로 파랑

두 가지가 겹쳐 있었다.
1. 스폰 정면을 막던 **진파랑 판은 그레이박스 버스**(정점 8개)였다. 실제 버스는 차도에 따로 있다.
2. 실제 버스는 머티리얼이 하나뿐이라(원본 텍스처를 로더가 벗긴다) 전체가 한 색이었다.

텍스처를 안 쓰므로 **면 높이로 영역을 나눠** 머티리얼을 줬다 —
차체 파랑 / 창문 띠(수직면만) / 하부 범퍼·바퀴 / 지붕. 서울 간선버스 실사 기준이다.

### 16.5 그 밖

- 정류장 표지판이 진행 방향(동쪽)에 서 있어 시야를 막았다 → 쉘터 서쪽 끝으로.
- 화장실은 문틀·사인만 있고 방이 없어 벽에 붙은 판처럼 보였다 → 방 매스를 짓고,
  충돌도 실제 방 범위로 줄였다(예전 5.0×3.0은 문틀보다 1.35 m 앞에서부터 막았다).
- 정류장 지붕이 폴 머티리얼(짙은 회색)을 써서 머리 위가 통째로 검었다 → 밝은 지붕 재질로.

### 16.6 드로우 콜 예산 상향 (160 → 180)

Z2가 정확히 160에 걸렸다. 상한을 올리기 전에 줄일 수 있는 것부터 줄였다
(화살표 메시 조건부 비표시).

그래도 넘는 이유는 낭비가 아니다 — 로더가 **머티리얼별로 병합**하므로
드로우 콜 수 ≈ 머티리얼 종류다. 원기둥 3종·점자블록 2종·줄눈·천장 리브·조명·덕트·
노선띠를 넣으면서 Z2에서만 머티리얼이 10종쯤 늘었다. 증가분은 곧 **추가한 마감의 개수**다.

진짜 상한은 `A-6 60fps 유지` 쪽이고 실측 최저 232 fps로 여유가 크다.
이 값을 또 올려야 하면 그때는 머티리얼 통합부터 검토한다.

### 16.7 쇼케이스 갱신

`index.html`은 이미지를 base64로 품은 2 MB짜리 한 파일이라 손으로 못 고친다.
`tools/update_showcase_map.py`가 MAP-01 카드의 9장을 순서대로 교체한다 —
alt를 대조해 어긋나면 멈춘다.

렌더는 Blender **Workbench**(플랫 + 캐비티)로 뽑는다. 게임의 툰 플랫 룩과 결이 맞고
EEVEE보다 빠르다. 두 가지를 꼭 해야 한다.
- **천장을 걷어낸다.** 위에서 보는 도해에 천장을 남기면 지붕만 찍힌다(처음에 그렇게 나왔다).
- **`material.diffuse_color`를 Principled 베이스 컬러로 동기화한다.** Workbench의
  MATERIAL 모드는 Principled가 아니라 뷰포트 표시 색을 읽는다 — 이걸 몰라서 첫 렌더가
  전부 회색으로 나왔다.

⚠ 렌더용으로 끈 `hide_render`는 **익스포트 전에 반드시 되돌린다.** 복구를 일괄로 돌리면
원래 의도적으로 숨겨 둔 중복 오브젝트까지 켜지므로(실제로 Z1이 170 → 171이 됐다)
복구 후 익스포트 오브젝트 수를 확인할 것.

## 17. 확인 루프를 Blender 안으로 — 웹 왕복 없애기

### 17.1 문제

맵을 고칠 때마다 **Blender → 익스포트 → 웹 → 확인**을 왕복했다. 한 번에 1~2분이고,
"아직 덜 고쳐졌다"를 알기 위해 매번 그 왕복을 해야 했다.

### 17.2 `tools/blender_preview.py`

Blender Scripting 탭에서 한 줄로 불러 쓴다.

```python
exec(open(r"C:\Users\User\Documents\HACKERTON\tools\blender_preview.py").read())

look("stair-mid")     # 게임과 같은 눈높이(1.62m)·화각(74°)으로 그 지점에서 본다
look(7.5, 28)         # 좌표로 직접
collision(True)       # 충돌 형상을 실제 지오메트리 위에 겹친다
spots()               # 지점 목록 (순회 촬영과 같은 좌표)
```

시점 지점은 `tests/e2e/tour.spec.ts`와 **같은 좌표**다. 웹에서 본 그림과 곧바로 대조된다.
눈높이·화각을 게임과 맞춘 게 핵심이다 — 안 맞추면 "웹에선 보이는데 여기선 안 보인다"가 생긴다.

### 17.3 충돌 오버레이 — 이 프로젝트에서 가장 값싼 버그 예방

`collision(True)`가 `world.ts`의 충돌 형상을 와이어로 겹쳐 그린다.
빨강=벽 · 파랑=바닥 · 초록=경사(실제 기울기로) · 노랑=유도선.

이 프로젝트에서 반복해서 물린 버그가 **전부 보이는 것과 막는 것의 어긋남**이었다.

| 버그 | 겹쳐 봤으면 |
|---|---|
| 계단이 충돌 램프보다 0.30 m 떠서 발이 디딤판을 뚫음 | 초록 경사면이 디딤판과 어긋난 게 바로 보인다 |
| 승강장 기둥이 충돌 없이 통과됨 | 빨강 박스가 없는 게 보인다 |
| 화장실이 문틀보다 1.35 m 앞에서 막힘 | 빨강 박스가 벽보다 튀어나온 게 보인다 |
| 유도선이 정류장 기둥·차단벽을 관통 | 노랑 선이 빨강 박스를 지나는 게 보인다 |

데이터는 `world.ts`에서 뽑는다 — 사본을 손으로 관리하면 그 사본이 또 어긋난다.

```
cd game && npm run dump:collision      # → game/tools/collision.json
```

### 17.4 로컬에서 게임 돌리기

배포까지 갈 필요가 없다. GLB를 다시 뽑고 브라우저만 새로고침하면 된다.

⚠ **강제 새로고침**(Ctrl+Shift+R)을 쓸 것 — GLB는 브라우저가 캐시한다.
이 프로젝트에서 "고쳤는데 그대로다"의 절반이 이것이었다.

## 18. 쇼케이스 — 캐릭터 카드 갱신과 스프라이트 시트 재현

### 18.1 무엇이 낡아 있었나

MAP-01 이미지는 §16.7에서 갈았지만 **플레이어 카드가 애니메이션 9종에서 멈춰 있었다.**
리그에는 `JumpAir`·`JumpLand`가 추가돼 11종이다. 목록 페이지의 요약 줄도 9종이었다.

### 18.2 스프라이트 시트 규격 — 문서가 아니라 파일에서 역산했다

시트를 만들던 세션의 카메라·조명 설정은 `.blend`에 남아 있지 않았다.
그래서 **기존 시트를 계측해 역산**했다. 순서가 곧 방법이다.

1. `index.html`에서 base64를 꺼내 JPEG로 저장 → 프레임 **170×220**, 시트는 가로 이어붙이기
2. numpy로 배경색과 캐릭터 바운딩 박스를 잰다 → 캐릭터가 프레임 높이의 **65 %**(143 px),
   가로 중앙, 상단에서 24 px
3. 그 수치를 만족하는 카메라 거리를 화각에서 역산하고, **렌더 → 계측 → 보정**을 2회 돌려 수렴

측면·정면을 둘 다 렌더해 폭을 재서 어느 쪽인지도 확인했다(정면은 프레임을 넘겼다).

### 18.3 색이 안 맞았고, 원인은 색공간이 아니라 유실이었다

첫 렌더는 배경이 거의 검게 나왔다. 뷰 트랜스폼을 AgX·Filmic·Standard로 바꿔 가며
재 봤지만 셋 다 목표(청회색)와 멀었다 — 셋 다 **무채색**이었다.
즉 원본은 지금 파일에 없는 배경 설정으로 뽑힌 것이고, 되찾을 수 없다.

역추적을 포기하고 방식을 바꿨다.

- `film_transparent = True`로 렌더해 **배경을 numpy에서 직접 합성**한다 (색을 정확히 지정)
- 캐릭터 톤은 원본에서 잰 평균값에 맞춰 게인을 계산한다 (0.795)

되찾을 수 없는 설정을 추측하느니, **원하는 결과를 직접 만드는 쪽**이 재현 가능하다.

### 18.4 수치는 문서가 아니라 데이터에서 센다

`tools/add_showcase_clips.py`는 카드를 넣은 뒤 `<article>` 수를 세어 헤더의 종수를 쓴다.
목록 페이지도 각 카드의 실제 클립 수에서 채운다. 손으로 적으면 또 어긋난다 —
이번에 낡아 있던 "9종"이 정확히 그렇게 생긴 값이다.

### 18.5 MAP-01 카드 본문

스펙에 이번 마감의 실측치를 더했다 — 기둥 원형 24본 · 계단 단너비 325/단높이 171 ·
점자블록 전 구간. 리드에는 "치수는 밸런스에서, 마감은 실사 계측에서 나왔다"는 근거를 적었다.

### 19.2 역 출입구 — 개구부가 아예 없었다

`Z1_OBJ05_entrance`의 서쪽 면이 y 25.9~30.0 · z 0.23~3.83을 **판 5장으로 통째로 막고

레이캐스트로 확정한 뒤 해당 면만 지오메트리 조건으로 골라 삭제했다

`Z1_entr_lintel`(z 2.55~3.83)을 새로 세워 사인 띠 뒤가 뚫리지 않게 했다.

비어 있던 흰 판 `Z1_entr_signplate`에 역명을 넣었다 — **홍대입구 / Hongik Univ.**
글자면 방향은 `rotation_euler = (π/2, 0, −π/2)`가 −X(서쪽)를 향한다.

### 19.3 승강장 천장이 하강 계단을 관통하고 있었다

가장 큰 결함. `Z5_ceiling`(z −15.50~−15.10)이 x 78~206 전체를 덮는 통짜 슬래브라
**하강 계단·에스컬레이터 샤프트를 가로질렀다.** 머리 위 여유가 x 113~116 구간에서
**0.40 m**였다 — 사용자가 "중간이 막혀 있다"고 한 지점과 정확히 일치한다.

슬래브를 샤프트(x 95.8~120.4 · y 0.95~9.60) 기준 4조각으로 다시 만들어 개구부를 뚫었다.
`Z4_wall_S`도 복도 남벽인데 x=120까지 뻗어 샤프트 안에 떠 있어 x=96에서 끊었다.

| 위치 | 전 | 후 |
|---|---|---|
| 계단 x 113 | 0.40 m | 2.44 m |
| 계단 x 116 | 1.97 m | 2.67 m |
| 에스컬 x 113 | 0.40 m | 2.71 m |

**계측 방법**: 바닥을 먼저 레이로 잡고 그 위에서 다시 위로 쏜다. 위에서 아래로만 쏘면
경사 천장을 바닥으로 오인한다(처음에 그랬다). 중앙 손잡이(y=6.70) 위를 걸으면 손잡이가
천장으로 잡히므로 y=5.5 / 8.0 두 줄로 잰다.

### 19.4 개찰구 6기 → 9기 · 피치 4.0 → 2.0 m

`GATES` 배열이 충돌·렌더·시드·테스트의 단일 출처라 배열만 바꾸면 전부 따라온다.
Blender에서는 G1(표준)·G6(우대)을 원본으로 복제해 베벨 모디파이어까지 보존했다.

- y = 8, 10, … , 24 · 우대용은 **G9**(0.90 m)
- 뱅크 폭 21.3 → **17.3 m**
- 게이트 사이·양끝은 `Z3_gate_glass`(유리 1.15 m + 상부 레일)로 막았다.
  충돌은 예전부터 `wallWithGaps`가 y 0~32을 막고 있었지만 **보이는 게 없어서
  통과할 수 있어 보였다** — 시각을 충돌에 맞춘 것이지 그 반대가 아니다.

**부수 효과 — S4-8이 저절로 충족됐다.** MAP §5.4의 원래 요구는 "게이트 6기 동시 가시"였고,
1인칭 화각 74°로는 불가능하다며 "고개를 돌리면 판독"으로 완화해 뒀었다.
피치를 좁히니 **동시 가시 최대 6기**가 나온다(`p0.spec.ts`가 하한 4기로 지킨다).

**밸런스 영향**: `rollSeed`는 여전히 정상 게이트를 1~2기만 뽑는다. 9기 중 1~2기라
탐색 비용이 오르는 것처럼 보이지만, 램프 색이 시드의 직접 투영이라 플레이어는
**보고 걸어간다** — 늘어나는 건 판단이 아니라 이동 거리다. 완주 테스트는 8시드 전부 통과.

### 19.5 화장실 — 통짜 박스에서 들어갈 수 있는 방으로

`Z2_OBJ14_room`은 5.0 × 2.05 m 상자에 픽토그램만 붙인 것이었다. 문도 안도 없었다.
`tools/build_wc.py`로 다시 짓는다 (13.0 × 4.0 m, 남 · 여 · 다목적).

대변기 부스 0.90~1.00 × 1.40~1.50 · 소변기 중심 간격 0.75~0.80 · 세면 카운터 높이 0.80 ·
통로 1.20 이상 · 다목적 2.00 × 2.00.

입구마다 **가림벽**을 세웠다. 실제 역 화장실이 그렇고, 없으면 대합실에서 안이 다 보인다.

충돌은 `world.ts`에 15개 솔리드로 같이 넣었다. **부스는 칸막이가 아니라 덩어리로 막는다** —
칸막이만 막으면 플레이어가 부스 안에 갇힌다.

### 19.6 드로우 콜 — 통합 먼저, 예산 상향은 그다음

## 20. 실사 대조 마감 — 선형 천장 · 자발광 · 유리 점포 (v2.0 · 2026-08-01)

실제 서울 지하철 승강장·대합실·개찰구 사진을 모아 우리 모델과 한 장씩 대조했다.
**렌더 두 줄이 지오메트리 수십 개보다 크게 바꿨다** — 그게 이번 라운드의 요지다.

### 20.1 렌더 — 실내가 통째로 어두웠던 두 원인

**① 아래를 향한 면이 실내에서 가장 어두웠다.** `scene.ts`의 광원이 전부 위에서
내려왔다(sun · hemi · fluor). 툰 셰이딩은 법선으로 밝기를 정하므로 천장·계단 밑면·
차양이 바닥보다 어둡게 나왔다. 실제 역은 정반대다 — 밝은 화강석 바닥이 빛을 되쏘아
**천장이 가장 밝다.**

```ts
const bounce = new DirectionalLight(PALETTE.fluor, 0.30)
bounce.position.set(-0.15, -1, -0.25)   // 유일하게 아래에서 위로
// setMood: 지하 0.34 · 지상 0.12 (아스팔트는 덜 되쏜다)
```

**② 조명이 조명으로 안 읽혔다.** 조명기구와 백라이트 광고판도 툰 셰이딩을 받아
주변보다 어두웠다. 광원은 음영을 받지 않는 게 맞다 — `SELF_LIT_MATERIALS`를 두고
`MeshBasicMaterial(toneMapped:false)`로 그린다.

`FIXTURE` `AD_PANEL{,2,3}` `LED_AMBER` `SH_GREEN` `SH_RED` `VM_LIGHT` `CHG_SCR`
`ESC_COMB`, 그리고 **`TXT_WHITE`** — 발광 띠 위에 툰 셰이딩된 흰 글자를 얹으면
회색이 되어 안 읽혔다. 안내 사인은 읽히는 게 존재 이유다.

### 20.2 승강장 천장 — 평 슬래브에서 선형 루버로

레퍼런스에서 가장 두드러진 것은 **길이 방향으로 반복되는 선형 알루미늄 루버**와
그 사이를 달리는 연속 라인 조명이다. 우리는 평평한 슬래브에 얇은 띠 2줄이었다.

- 핀 163개 · 피치 0.60 m · 깊이 0.16 m (기둥 캡·샤프트 개구부는 건너뛴다)
- 라인 조명을 **루버 아래(z −15.71)** 로 내렸다. 천장면과 같은 높이에 두면 핀에 가린다

시선이 낮을수록 핀 측면이 개구를 덮어 루버가 닫힌다 — 실제 사진과 같은 원근 리듬이 나온다.

### 20.3 지난 라운드가 남긴 결함 두 개

**천장 개구부를 너무 크게 뚫었다.** §19.3에서 하강 샤프트를 x 95.8~120.4 전 구간 뚫었는데,
계단이 승강장 천장(−15.50) **아래로** 내려오는 건 x ≈ 112.3부터다. 그 서쪽은 계단이
천장 위에 있으므로 뚫을 이유가 없었고, 뚫은 탓에 승강장에서 계단 밑면이 드러났다.
→ 개구부를 **x 111.8~120.4** 로 좁히고 가장자리에 테두리 보를 세웠다.

**Z4 계단에 하부 마감이 없었다.** Z1에는 `Z1_st_underside`가 있는데 Z4에는 없어서
디딤판·챌판이 날것으로 보였다. 계단면을 0.4 m 간격으로 레이 샘플링해 그대로 따라가는
사판을 만들었다 — **계단참(x 107~108.6)이 있어서 직선 프리즘으로는 안 맞는다.**
바닥(−20.00)을 뚫기 직전(x 118.6)에서 끊는다.
